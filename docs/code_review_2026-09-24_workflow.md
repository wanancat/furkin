## 1. 工作流目标

本工作流用于安全地完成审查报告中的整改，确保：

1. 高严重度问题优先处理，但不破坏相互依赖的数据、协议和 AI 生命周期。
2. 每个工作包范围清晰、改动集中、验证证据完整。
3. 静态编译通过不等于运行期通过，客户端、服务端、网络和数据包场景分别验证。
4. 不在修复过程中引入第二套注册体系、全局文本替换或未经核对的旧版本 API。
5. 公开行为、网络协议、技能 schema、语言文件、版本号和 changelog 同步维护。
6. 发现范围外问题时单独登记，不顺手扩大当前工作包。

## 2. 工作原则

### 2.1 小步实施

- 一个工作包只解决一个内聚问题，或解决一组强耦合问题。
- H-02 与 M-03 存在技术依赖，必须按本文顺序处理，不能先删除 goal 再讨论恢复机制。
- 修 H-01 时若改变确认包字段、编码或语义，必须同时把 M-01 拉入该工作包，不能等到后续批次。
- M-02 与 M-04 都涉及技能定义和运行时效果，可以在同一工作包内设计，但提交和验证要能区分退款/schema 与热重载效果。

### 2.2 服务端权威

- 客户端只能提交请求，所有可改变持久状态的动作都必须由服务端重新校验。
- 网络包中的实体 ID、页签、名称、模式、技能 ID 和客户端显示数据都不能直接视为可信输入。
- 任何“客户端已经校验过”的说明都不能替代服务端校验。

### 2.3 证据优先

每个工作项至少记录：

- 基线提交和工作分支。
- 设计决策及未采用方案。
- 修改文件及原因。
- 执行的命令、测试环境和结果。
- 运行日志中的 `ERROR`、`FATAL`、异常栈、注册失败和资源缺失检查结果。
- 尚未执行的验证、已知限制和残余风险。

禁止用以下内容代替验证：

- 仅凭编译通过推断运行期通过。
- 仅凭静态引用推断专用服务端崩溃。
- 仅凭代码注释推断原版或第三方 AI 已恢复。
- 删除日志、回写成功记录或伪造测试结果。

### 2.4 显式状态

- 未开始：`待排期`
- 正在确认方案：`设计确认`
- 正在修改：`实施中`
- 代码完成、等待质量检查：`待静态验证`
- 静态检查通过、等待实机：`待运行验证`
- 实机验证通过：`待文档/版本`
- 全部完成：`已完成`
- 因 EULA、环境或外部阻塞：`阻塞`

状态只能前进，不能跳过验证门槛。若实现变更使先前验证失效，状态退回相应阶段并重新验证。

### 4.1 技术依赖覆盖

审查报告建议先做 H-02、再做 M-03，但 H-02 需要清理战斗 AI。若没有 M-03 提供的“本模组 goal 所有权/原始状态恢复”机制，H-02 只能继续按基类删除 goal，无法满足“解绑后行为无残留且不破坏第三方 AI”。

1. 先设计并实现 M-03 的最小 goal 标记/恢复机制。
2. 再用该机制完成 H-02 的 AI 清理。
3. M-03 的完整兼容回归可以在 WP-02 一并完成，不再留到后续批次补救。

H-01 与 M-01 的关系同理：如果 H-01 增加 token、会话字段或改变包语义，M-01 不再是独立后续项，而是 WP-01 的必要条件。

## 5. 标准执行流程

### 5.1 阶段 0：建立工作记录

**输入**

- 审查报告中的问题 ID。
- 当前分支、HEAD 和工作区状态。

**动作**

1. 复制该问题的工作项模板。
2. 记录严重度、影响、依赖和非目标。
3. 确认问题在当前代码中仍可复现或仍有静态证据。
4. 若报告行号已变化，重新定位并记录新位置。

**出口条件**

- 问题范围明确。
- 依赖项明确。
- 是否存在 EULA 或运行环境阻塞已标记。

### 5.2 阶段 1：代码勘察与方案设计

**动作**

1. 检索所有调用点，不只看报告列出的单点。
2. 对 1.20.1 / Forge 47.2.0 API 使用 `javap`、mappings 或官方源码核对签名和语义。
3. 明确数据流：客户端输入、网络方向、服务端校验、持久化、客户端同步。
4. 明确失败路径：非法输入、目标消失、重复请求、维度切换、断线、重载、存档加载。
5. 写明兼容策略和迁移策略，区分旧数据、新数据和无数据。
6. 列出本轮不修的相关问题。

**输出**

- 设计摘要。
- 文件级改动清单。
- 测试矩阵。
- 未决问题和是否阻塞实施。

**出口条件**

- 设计没有依赖私有 API、反射或旧版本存在性推断。
- 客户端/服务端边界明确。
- 若影响公开 API、协议或数据格式，已确定版本/文档影响。

### 5.3 阶段 2：实施

**动作**

- 按最小可验证改动实施，不顺手重构。
- 新增网络包或字段时同步更新两端处理器、方向和协议版本。
- 新增玩家可见文本时同步添加 `en_us.json` 与 `zh_cn.json` 键。
- 修改技能 schema、加载逻辑或内置技能时同步 `SKILL_TREE.md`。
- 修改公开行为、API 或用户可见修复时同步 README/changelog。
- 每个内聚步骤至少运行 `compileJava`。

**出口条件**

- 目标问题有直接代码路径覆盖。
- 未新增已知的服务端权威缺口。
- 没有提交 `build/`、`.gradle/`、`run/`、日志、IDE 文件或生成 jar。

### 5.4 阶段 3：静态质量门槛

按影响范围执行：

```powershell
$env:JAVA_HOME = 'C:\Program Files\Java\jdk-17.0.2'
$env:Path = "$env:JAVA_HOME\bin;$env:Path"

.\gradlew.bat compileJava --console=plain
.\gradlew.bat build --console=plain
```

并检查：

- [ ] Java 编译通过。
- [ ] 资源处理通过。
- [ ] 所有 JSON 可解析。
- [ ] `en_us.json` 与 `zh_cn.json` 键集合一致。
- [ ] `mods.toml` 等展开资源未引入非法裸 `$`。
- [ ] `PROTOCOL_VERSION` 与包结构/字段变化一致。
- [ ] 没有新增共享源码对 `net.minecraft.client.*` 的直接依赖。
- [ ] Git diff 中不存在与工作项无关的改动。

**出口条件**

- `build` 通过。
- 静态检查结果被记录。
- 进入运行验证前不再计划修改实现。若修改，则重跑本阶段。

### 5.5 阶段 4：代码复核

复核至少覆盖：

- [ ] 服务端是否重新校验所有客户端可控字段。
- [ ] 失败路径是否在写持久状态或扣物品前返回。
- [ ] 是否可以重复请求、竞态请求或跨维度请求。
- [ ] 解绑/死亡/收回/重召唤的生命周期是否闭合。
- [ ] 存档旧数据是否可加载，是否需要迁移。
- [ ] 技能/属性 modifier 的添加与移除是否成对。
- [ ] AI goal 是否只操作本模组拥有的实例，原始状态是否可恢复。
- [ ] 网络版本、方向、编码顺序和处理器是否一致。
- [ ] 语言键、版本号、README、changelog 和 SKILL_TREE 是否按影响同步。

### 5.6 阶段 5：运行验证

按工作项选择：

```powershell
.\gradlew.bat runServer --console=plain
.\gradlew.bat runClient --console=plain
```

运行后检查 `run/logs/latest.log`：

- 不允许新增 `ERROR`、`FATAL`、异常栈、注册失败或资源缺失。
- 启动成功但日志报错不算通过。
- 客户端与服务端共享协议变更时，两端都要验证。
- 专用服务端类加载问题必须使用真实服务端验证，不能只靠 `build`。

若缺少 EULA、环境或用户未确认运行条件：

- 将状态设为 `待运行验证` 或 `阻塞`。
- 明确记录未执行命令和原因。
- 不得把静态结论写成实机通过。
- 不得代替用户接受 EULA。

### 5.7 阶段 6：文档、版本与变更记录

- 公开 API 变化：按 `AGENTS.md` 判断是否递增 `MAJORAPI`。
- 新增机制：通常递增 `MINOR`；纯缺陷修复：递增 `PATCH`。
- 网络语义变化：协议版本和双端验证同步。
- 技能数据格式变化：同步 `SKILL_TREE.md`。
- 用户可见变化：同步 `CHANGELOG.md` 和 `changelog.en.md`。
- 安装或 API 说明变化：同步 `README.md` 和 `README.zh-CN.md`。
- 版本元数据只从 `gradle.properties` 修改，不只手改注释或资源。

### 5.8 阶段 7：关闭工作项

关闭前重新确认：

- [ ] 原问题已被代码路径覆盖，而不是仅在文档中声称修复。
- [ ] 所有适用验证已执行并记录结果。
- [ ] 未满足的验证有明确的阻塞原因和后续动作。
- [ ] 没有新增同类未追踪问题。
- [ ] 文档、版本和 changelog 已完成或明确不需要。
- [ ] 用户未要求的提交、推送、EULA 接受均未发生。

全部满足后状态才改为 `已完成`。

### 6.1 WP-01：契约确认的服务端权威化（H-01）

#### 目标

让确认包只能完成服务端已认可、仍有效且状态未变化的契约操作。

#### 设计步骤

1. 决定待确认会话的绑定字段：玩家、目标稳定标识、维度、发起 tick/TTL、物品堆叠和名称约束。
2. 确认会话的创建点、替换规则、成功后清理、超时清理、登出清理和目标卸载处理。
3. 在确认处理阶段按顺序复检：
   - 注册物种；
   - 能力存在；
   - 尚未契约；
   - 活跃上限；
   - 存活、未移除、距离/可达；
   - 主手物品与数量；
   - 名字长度、内容和安全约束。
4. 所有校验通过后才扣物品、写能力数据、建档案和同步客户端。
5. 若请求字段或包语义发生变化，同步递增 `PROTOCOL_VERSION`，把 M-01 纳入本工作包。

#### 必须覆盖的测试

- [x] 正常契约成功，物品只消耗一次。
- [x] 未注册实体伪造确认被拒绝。
- [x] 玩家实体伪造确认被拒绝。
- [x] 发起后切换主手或移走物品，确认被拒绝。
- [x] 目标死亡、移除或离开可达距离，确认被拒绝。
- [x] 目标跨维度后，旧确认不能作用于错误实体。
- [x] 连续发送两次确认，不重复建档、不重复扣物品。
- [x] 会话超时和登出清理入口已实际验证。
- [ ] 目标卸载后重载、服务器重启后的会话失效待验证。

#### 关闭条件

- 服务端是唯一结算点。
- 非法请求无法写持久状态。
- 上述运行期测试有实际结果。

#### 实施状态（2026-09-24）

- 状态：服务端核心完成；完整客户端与部分生命周期集成验证待办。
- 已完成：服务端待确认会话、600 tick TTL、目标 UUID/实体 ID/维度绑定、单次消费、主手槽位与堆叠快照、可达距离、名称校验、登出清理入口。
- 实际验证：两轮共 26 项服务端夹具用例通过；其中发现并修复 `canReach(target, 3.0D)` 距离校验缺失。
- 静态与运行验证：`compileJava`、`build`、`runServer`、`runClient` 启动通过；最终 JAR 不含临时夹具。
- 残余验证：真实客户端命名界面与网络实机、目标卸载重载、实体 ID 复用或同位置重建、服务器重启、真实 `PlayerLoggedOutEvent` 事件链。

### 6.5 WP-05：技能退款、schema 与热重载一致性（M-02 + M-04）

#### 目标

6. 为流血等临时效果选择策略：施加时快照参数，或明确声明 `/reload` 会改变当前效果。
7. 同步更新 `SKILL_TREE.md`、技能相关 changelog 和必要的语言键。

#### 必须覆盖的测试

- [ ] `tier`、`requiresLevel` 非法值被拒绝。

#### 关闭条件

- 重载后的实体效果与当前定义或明确快照语义一致。

### 6.6 WP-06：客户端类隔离（L-01）

#### 目标

共享网络包和共享处理路径不加载客户端类，专用服务端启动安全。

#### 实施步骤

1. 列出共享包对 `Minecraft`、Screen 等客户端类的直接引用。
2. 共享包只保留协议数据、encode/decode 和服务端校验。
3. 客户端处理逻辑移动到明确的 client-only handler。
4. 使用 Forge 安全分发入口隔离客户端类引用，确认服务端不会加载对应类。
5. 在专用服务端执行启动、进服和网络交互验证。

#### 关闭条件

- 共享源码不直接引用 `net.minecraft.client.*`。
- `runServer` 无 `NoClassDefFoundError`、类加载异常或网络处理异常。
- 不能只凭静态判断宣称专用服务端安全。
