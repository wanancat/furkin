## 2. NV-01：跟随绒亲的自动传送触发距离

### 2.1 现象与当前证据

- 玩家实测反馈：绒亲的自动跟随传送触发距离偏远，印象中接近 64 格。
- 当前 Furkin 源码没有注册独立的自动跟随传送 goal，也没有对应服务端配置项。
- 猫、狗继续使用原版 `net.minecraft.world.entity.ai.goal.FollowOwnerGoal`。
- `FurkinCombatMode.applyTo` 只捕获和移除战斗冲突 goal；`FollowOwnerGoal` 被有意保留。
- 1.20.1 / Forge 47.2.0 的原版 `FollowOwnerGoal` 字节码显示：
  - `TELEPORT_WHEN_DISTANCE_IS = 12`
  - `tick()` 在 `distanceToSqr >= 144.0` 时调用传送，对应 12 格。
- 因此“64 格”目前只是玩家侧观察，尚未与代码阈值对应。需要先排除实体所在区块未加载、模拟距离、服务端 tick 范围等因素造成“看起来更远才传送”。

### 2.2 目标

- 明确并复现实际触发距离，区分原版 goal 阈值与实体加载/tick 范围。
- 若仍需缩短，提供受控、服务端权威、可验证的自动传送距离。
- 不破坏原版 `FollowOwnerGoal` 的寻路、坐下、拴绳、乘客和第三方 AI 兼容行为。

### 2.3 可能实现方向

1. 新增 Furkin 自有跟随 goal，替代契约宠物的原版 `FollowOwnerGoal`，并纳入现有 goal 所有权与恢复机制。
2. 在 `FurkinCombatMode` 的捕获/恢复流程中区分 `FollowOwnerGoal`，解绑时恢复原实例和优先级。
3. 在 `FurkinServerConfig` 增加服务端配置，例如 `followTeleportDistance`：
   - 使用格数配置；
   - 默认值待复现和平衡后确定；
   - 设置合理上下限；
   - 明确 `0` 或关闭值是否表示禁用自动传送。
4. 若采用服务端 tick 兜底，只能作为备选方案，因为它会与原版寻路职责重叠，容易产生双重传送或卡顿。

### 2.4 验收条件

- [ ] 在同一维度和实体正常 tick 范围内，复现并记录实际触发距离。
- [ ] 配置生效后，跟随绒亲在目标距离触发传送，不发生重复传送。
- [ ] 坐在原位、拴绳、乘客、目标战斗状态下的行为有明确语义。
- [ ] 解绑后原版 goal 的行为和优先级可恢复，不误删第三方 goal。
- [ ] `compileJava`、`build`、`runServer` 和必要时的 `runClient` 通过。
- [ ] 日志无新增 `ERROR`、`FATAL`、异常栈、注册失败或资源缺失。

### 2.5 待确认问题

- 目标距离应设为多少格，是否需要面向整合包开放配置。
- 是否只调整 `FOLLOW` 模式，还是所有非坐下状态统一适用。
- 跨维度或长时间实体未加载时，是否仅依赖玩家主动召唤，不扩大自动传送范围。
- 是否需要将该事项拆成“原版阈值确认”和“可配置覆盖”两个工作包。

## 3. NV-02：玩家攻击自身及队友绒亲的友伤配置

### 3.1 当前行为

- 当前 `CommonEvents` 没有玩家对绒亲的友伤过滤。
- 玩家可以直接攻击自己的绒亲，也可能攻击同一队伍中其他玩家的绒亲。
- 现有最早段受击入口为 `CommonEvents.onLivingAttack`，适合在伤害、受击闪帧和音效之前取消友伤。

### 3.2 目标

- 新增服务端配置项，语义为“阻止玩家伤害自身及队友的绒亲”。
- 默认值应为开启，即默认不可攻击自身及队友绒亲。
- 关闭配置后恢复原版行为。
- 服务端认为应拦截时，必须在最早受击阶段干净取消，不留下伤害、闪帧、音效或仇恨副作用。

### 3.3 语义边界

- “自身绒亲”：受击实体是契约宠物，且其档案 `ownerUuid` 等于攻击玩家 UUID。
- “队友绒亲”：受击实体所属主人与攻击玩家处于同一原版计分板队伍。
- 需要明确“攻击”的范围：
  - 至少覆盖玩家直接近战和箭矢等由玩家造成的伤害；
  - 是否覆盖玩家放置 TNT、爆炸、间接伤害等，实施前必须定案。
- 需要明确主人离线时的队友判断方法。当前档案只保存 `ownerUuid`，没有主人名称；若要用原版计分板队伍判断离线主人的归属，可能需要补充可验证的归属或队伍快照。
- 是否需要同时阻止宠物之间的友伤，暂不默认扩大；本项先聚焦玩家攻击自身及队友绒亲。

### 3.4 可能实现方向

1. 在 `FurkinServerConfig` 增加服务端布尔配置，例如 `preventFriendlyCompanionDamage`，默认 `true`。
2. 在 `CommonEvents.onLivingAttack` 增加友伤判定，优先于被动和 `LivingHurtEvent` 结算。
3. 判定目标是否为已契约且在场的绒亲，并读取其档案 `ownerUuid`。
4. 提取攻击玩家，判断是否为目标主人，或是否与目标主人处于同一计分板队伍。
5. 命中友伤规则时取消 `LivingAttackEvent`，避免受击流程继续执行。
6. 为配置关闭、主人离线、目标非绒亲、无队伍和跨队伍场景补充测试。

### 3.5 验收条件

- [ ] 默认配置下，玩家不能伤害自己的绒亲。
- [ ] 默认配置下，玩家不能伤害同一计分板队伍中其他玩家的绒亲。
- [ ] 不同队伍的玩家仍可按服务器规则攻击对方绒亲。
- [ ] 配置关闭后恢复当前可攻击行为。
- [ ] 拦截发生在最早段，不出现闪红、音效、伤害、击退或仇恨变化。
- [ ] 直接攻击和最终选定的间接伤害类型均覆盖。
- [ ] 主人离线场景有确定且可测试的语义。
- [ ] `compileJava`、`build`、`runServer` 和必要的 `runClient` 通过。
- [ ] 日志无新增 `ERROR`、`FATAL`、异常栈、注册失败或资源缺失。

### 3.6 待确认问题

- 队友以原版计分板队伍为唯一口径，还是需要绑定 Furkin 自有队伍概念。
- 配置是否只拦截玩家直接攻击，还是拦截所有玩家归属伤害。
- 是否需要在绒亲录或配置注释中明确说明该保护行为。
